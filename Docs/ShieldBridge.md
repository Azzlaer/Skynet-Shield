# Universal ShieldBridge SDK — v0.10.0-alpha

Windows native bridge, C ABI version 1.0. Separate from client Shield DLL. Build Win32 for the current GameServer. The header uses fixed-width integers, caller-owned token output (65 bytes), opaque context, explicit cdecl, and DLL-owned allocation. Import library linking is the supported initial method. No STL objects cross the boundary. Compatibility with the actual v140 host is a design objective, not verified yet.

Configure a trusted DNS hostname, HTTPS port and a private GameServer service key via server-only configuration/environment. Never ship the service key to clients. Call Init once; Login only after successful independent player authentication, using a unique opaque session ID per connection (never reuse a character slot). Transfer only the returned token and expiry over an authenticated confidential channel to the matching client. Logout revokes the opaque session. Shutdown after all pending requests finish. All calls synchronous; schedule on a bounded backend worker, not on game tick or inside DllMain. Serialize login/logout/renewal for each session; stale operations must not overwrite newer grants. If issue response is lost, revoke or rotate under the same serialized lifecycle. The caller owns scheduling, retry policy and grant delivery. No automatic bans.

The current service emits compact JSON with token then expires_in; v1 bridge intentionally accepts that exact shape. TLS 1.2/1.3 uses Windows trust, no redirects or proxy. Timeouts are per operation, not a total deadline. No raw secrets should be logged. Credential copy is cleared at context destruction, but other process/transport copies may exist. Tests cover invalid inputs, not live TLS. API version check and import library are required for future upgrades.

Reference repositories SkynetMU_Source and SkynetMU_Source_Main are read-only; no patches or commits there. GameServer v140 and Main DLL v143 were observed in their project files. Integrate at authorized login/logout handlers after verifying the current code, not guessed offsets. Multi-instance credentials, event reporting, session status, action analysis, XML loader, and source-level wiring remain future work. The existing server has a single GameServer service key; this SDK does not yet isolate multiple servers.
